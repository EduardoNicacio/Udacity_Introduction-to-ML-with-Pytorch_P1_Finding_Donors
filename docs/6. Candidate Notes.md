## 1. Elevator Pitch

**The Problem:** A fictitious charity, *CharityML*, wants to send donation-request letters only to people likely to donate. Their research shows donors overwhelmingly earn more than $50,000 a year, but income cannot be observed directly in public records. With nearly 15 million working Californians to choose from, guessing wastes postage and annoys non-donors - so CharityML needs a model that identifies >$50K earners from the 13 public census features available per person.

**The Solution:** A complete supervised-learning workflow in `finding_donors.ipynb`: explore the 45,222-record 1994 U.S. Census dataset (24.78% earn >$50K), log-transform and min-max scale the skewed features, one-hot encode the categorical features into **103 columns**, and establish a naive-predictor floor (accuracy 0.2478, F-score 0.2917). Three candidates - **Gradient Boosting, Random Forest, and Logistic Regression** - are trained through a reusable `train_predict()` pipeline at 1%, 10% and 100% of the training set and scored with an **F<sub>0.5</sub> score** (precision-weighted, because a wasted letter costs more than a missed donor).

**The Result:** Gradient Boosting wins at every training-set size (test F-score 0.7395 vs 0.6813 for Random Forest and 0.6826 for Logistic Regression), and a 135-fit `GridSearchCV` (best: `learning_rate=0.05`, `max_depth=5`, `n_estimators=300`) lifts it to **accuracy 0.8706 / F-score 0.7516**. The model's top-5 features (marital-status, education-num, capital-gain, capital-loss, age) carry ~91% of total importance; training on only those 5 still yields 0.8590 / 0.7252. The notebook executes end-to-end with **13/13 cells, 0 errors**, and is exported as `docs/report.html`.

## 2. Architecture & Design Decisions

### Key Design Decisions

| Decision | Rationale |
| :--- | :--- |
| **F<sub>0.5</sub> score as the headline metric, not accuracy** | The classes are skewed (75% are <=50K), so accuracy can look fine while the model is useless. The project brief states that misclassifying a non-earner as a donor is *worse* than missing a donor (wasted postage), so precision is weighted 2x over recall via beta=0.5 |
| **Naive predictor computed before any model** | A model that blindly predicts ">50K" scores 0.2478 accuracy / 0.2917 F-score. Establishing this floor first turns every later number into a meaningful comparison instead of an isolated score |
| **Log transform + MinMax scaling on the 5 numeric features** | `capital-gain`/`capital-loss` are extreme right-skewed (most rows are 0, a few are >10,000); log(x+1) compresses the range so one outlier cannot dominate splits, and scaling keeps numeric features on equal footing |
| **One-hot encoding with `pd.get_dummies`** | The 8 categorical columns have no intrinsic order (workclass, occupation, ...). Dummy columns let the model use each category as an independent signal without inventing a fake ordinal ranking. Result: 103 features |
| **Fixed seeds everywhere (`random_state=42`, split `random_state=0`)** | Every score in the report must be reproducible on re-execution. The model seed (42) and the notebook's split seed (0) are never changed mid-project |
| **Three-model bake-off through one shared `train_predict()` pipeline** | Timing, accuracy and F-score are only comparable if measured identically. One function fits, predicts on `X_test` + the first 300 training rows, and records `train_time`/`pred_time` for all three learners |
| **`GridSearchCV` with `cv=5`, scoring=F<sub>0.5</sub>, and no `max_features`** | Hyperparameters are chosen by cross-validation on the *training* set only; the test set is touched once per model. `max_features` is deliberately not tuned, per project instructions |
| **Model choice justified by learning curves, not one score** | Each learner is run at 1%, 10% and 100% of training data. This exposes overfitting (Random Forest hits F=1.0000 on training data yet 0.6813 on test) and shows Gradient Boosting improving steadily with data |

### Why Not

- **Support Vector Machine / K-Neighbors?** Both are competitive on paper but scale poorly to 45k rows x 103 features (kernel SVM training time grows quadratically), they produce no `feature_importances_` - which the rubric requires later - and their hyperparameter search spaces are far more expensive to tune.
- **Deep learning?** Overkill for a 45k-row tabular dataset; would add framework weight (this is a PyTorch course, but the notebook's rubric is scikit-learn based), training time, and hyperparameter risk while usually matching gradient boosting on tabular data.
- **SMOTE / class-weight rebalancing?** The imbalance is handled the way the project intends: choose a metric (F<sub>0.5</sub>) that reflects the business cost of errors, and judge against the naive baseline. Resampling would deviate from the prescribed pipeline and distort probability estimates.
- **Tuning `max_features` in the grid?** Explicitly disallowed by the project instructions ("Avoid tuning the `max_features` parameter"); the grid explores `n_estimators`, `learning_rate` and `max_depth` instead - 3 parameters x 3 values each.

## 3. Pipeline Design Principles in Practice

This project is a notebook, not a service - but the same engineering instincts apply. The "patterns" here are methodological rather than object-oriented.

### The Baseline Floor - Measure Before You Model

```txt
┌───────────────────────────────────────────┐
│ Naive predictor (always predicts ">50K")  │
│ accuracy = precision = 0.2478             │
│ recall    = 1.0     (no false negatives)  │
│ F0.5      = 0.2917                        │
└───────────────────────┬───────────────────┘
                        │ every model must clear
                        ▼
        Gradient Boosting  0.7395   (2.5x the floor)
        Logistic Regression 0.6826
        Random Forest       0.6813
```

The naive predictor is computed from first principles (`TP`, `FP`, `beta=0.5` formula) *before* any learner runs, and the same values are later drawn as dashed reference lines in `vs.evaluate()`. It is the project's unit-test equivalent: if a "trained" model could not beat it, the pipeline would be broken.

### Reproducibility by Contract

| Knob | Value | Why |
| :--- | :---: | :--- |
| Train/test split seed | `random_state=0` | Fixed by the notebook template; never touched |
| Model seed | `random_state=42` | Applied to GBC, RF, LR, and the feature-importance model |
| Metric | `beta=0.5` | Same `fbeta_score` argument everywhere, including the grid-search scorer |
| Environment | Python 3.14.7, scikit-learn 1.9.1, pandas 3.0.6, NumPy 2.5.1, matplotlib 3.11.2 | Recorded in the notebook intro so a reviewer can reproduce the exact numbers |

Re-running the notebook regenerates every table and figure byte-for-byte (up to timings), which is what makes claims like "test F-score 0.7395" checkable rather than anecdotal.

### Evaluation Hygiene (Single Responsibility per Data Split)

```txt
X_train (36,177)  ──►  fitting + cross-validation (GridSearchCV cv=5)
X_test  ( 9,045)  ──►  scored once per model, never used to choose hyperparameters
X_train[:300]     ──►  training-subset score, only to detect overfitting (train vs test gap)
```

The optimized model's parameters (`learning_rate=0.05`, `max_depth=5`, `n_estimators=300`) were selected exclusively from validation-fold scores inside `GridSearchCV`. The test set is only read afterward to report the final 0.8706 / 0.7516 - a small but real firewall against overfitting the benchmark.

### Interpretability as a Required Deliverable

```txt
manual ranking (Q6, written blind)     model ranking (Q7, from feature_importances_)
1. capital-gain                        1. marital-status_ Married-civ-spouse  0.3940
2. age                                 2. education-num                       0.2017
3. education-num                       3. capital-gain                        0.2000
4. hours-per-week                      4. capital-loss                        0.0627
5. occupation                          5. age                                 0.0543
              └────────── 3 of 5 matched ──────────┘
```

Ranking the features *before* looking at the model turns feature importance into a genuine test of understanding (and a great discussion prompt for Q7), instead of a chart nobody reasoned about. The follow-up ablation - retraining on only the top 5 features - then quantifies how much of the signal those columns actually hold (~91%, costing just 2.64 F-points when dropped to 5 features).

## 5. Evaluation & Verification Philosophy

### Why Accuracy Is Banned as the Headline Number

```txt
Class balance:  <=50K  34,014 (75.22%)   |   >50K  11,208 (24.78%)

"Always predict <=50K"  → accuracy 0.7522, recall 0.0000, F0.5 = 0.0000  ← useless
"Always predict >50K"   → accuracy 0.2478, F0.5 = 0.2917                 ← the Q1 floor
Optimized model         → accuracy 0.8706, F0.5 = 0.7516                 ← actual skill
```

Both trivial rules beat or nearly beat one another on accuracy while being worthless. That is precisely why the project standardizes on **F<sub>0.5</sub>** (precision-weighted) and reports it beside accuracy everywhere.

### The Verification Pyramid

```txt
        ┌─────────────────────────┐
        │  Report export          │  ← docs/report.html carries every output + plot
       ┌┴─────────────────────────┴┐
       │  Full notebook execution  │  ← nbconvert aborts on the first error
      ┌┴───────────────────────────┴┐
      │  Static checks              │  ← 13/13 cells compile, 0 '= None' stubs,
     ┌┴─────────────────────────────┴┐    7/7 answer cells filled, nbformat valid
     │  Independent recompute        │  ← naive baseline & learning curves re-derived
     └───────────────────────────────┘    from raw CSV with identical seeds
```

### Key Evaluation Insights

**1. Sanity targets before execution.** The exploration and Q1 numbers were computed by hand from the raw CSV first (45,222 / 11,208 / 24.78%; naive F = 0.2917). When the notebook later printed exactly those values, the pipeline's data handling was confirmed - including label encoding and the train/test split ratio.

**2. A score without a learning curve is half a result.** Running every learner at 1%, 10% and 100% of the training set separates "learns well" from "memorizes well":

| Model | Test F @ 1% | @ 10% | @ 100% | Train F @ 100% | Verdict |
| :--- | :---: | :---: | :---: | :---: | :--- |
| Gradient Boosting | 0.6596 | 0.7211 | **0.7395** | 0.7341 | Healthy - improves with data, train/test gap small |
| Random Forest | 0.6201 | 0.6685 | 0.6813 | 0.9706 | Overfits - near-perfect training F, 29-point test gap |
| Logistic Regression | 0.6390 | 0.6783 | 0.6826 | 0.6903 | Plateaus - a linear boundary caps its performance |

**3. Tuning must be validated, not asserted.** The grid's 27 candidate settings are scored by 5-fold CV on the training set; the reported gain (0.7395 -> 0.7516 F) is measured on data the search never saw.

**4. Interpret the model, don't just deploy it.** `feature_importances_` (~91% concentrated in 5 columns) plus the 5-feature ablation (0.8590 / 0.7252) answer the follow-up question every stakeholder asks: "what actually drives this, and do we need all of it?"

## 6. Challenges & Resolutions

### Challenge 1: An Environment With No ML Stack (Python 3.14)

**Symptom:** The very first import check failed with `ModuleNotFoundError: No module named 'sklearn'` - the machine had Jupyter and NumPy, but no pandas, scikit-learn or matplotlib, and only Python 3.14 was installed.

**Root Cause:** The project assumes an Anaconda-style distribution (or the Udacity workspace) that pre-installs the stack; this machine had a bare Python 3.14.

**Fix:** Before installing anything, `pip install --dry-run` confirmed cp314 wheels exist for the needed versions, then a single global install brought in pandas 3.0.6, scikit-learn 1.9.1, matplotlib 3.11.2 (pulling scipy 1.18.1, joblib, threadpoolctl).

**Takeaway:** Verify toolchain availability *before* planning execution - a wheel-availability check is cheaper than a failed 30-minute run.

### Challenge 2: Cross-Cell Dependencies and Label Formatting Traps

**Symptom:** The data-exploration cell sits *above* the cell that defines `income_raw`, so the obvious `income_raw.str.strip()` would have raised `NameError`. Separately, the project brief warns the income labels may carry a leading space (`" >50K"`), which would make a naive equality check silently return 0 positives.

**Fix:** The exploration cell works directly from `data['income']`, and every label comparison uses defensive normalization: `(data['income'].str.strip() == '>50K')`. Encoding later uses the same pattern on `income_raw`.

**Takeaway:** In notebooks, execution order *is* the dependency graph - read the whole notebook before editing any cell.

### Challenge 3: The README's Dataset Size Was Wrong

**Symptom:** The starter README says "approximately 32,000 data points", but line counts on `census.csv` showed 45,223 lines including the header.

**Fix:** Treated the data as the source of truth: computed `n_records = data.shape[0]` (45,222) and derived the class counts from the file itself rather than trusting documentation, then re-verified with a second parse (34,014 + 11,208 = 45,222). All downstream ratios (24.78%, the 36,177/9,045 split, the 1% and 10% sample sizes) follow from the actual file.

**Takeaway:** Documentation describes intent; the dataset is the contract. Sanity targets computed from raw data double as test fixtures for the rest of the project.

### Challenge 4: A 135-Fit Grid Search Inside One Notebook Cell

**Symptom:** `GridSearchCV` over 27 parameter combinations with `cv=5` means 135 `GradientBoostingClassifier` fits on 36,177 x 103 data - easily the slowest step, and a dead kernel or a default 30-second cell timeout would destroy the run.

**Fix:** `GridSearchCV(clf, parameters, scoring=scorer, cv=5, n_jobs=-1)` to parallelize across folds, executed with `--ExecutePreprocessor.timeout=3600` (1 hour per cell), in a single pass so the whole notebook stays one reproducible execution. `max_features` was left out of the grid per instructions, which also kept the search space honest.

**Takeaway:** Budget for the slow cell explicitly - parallelize folds, raise the timeout, and keep the expensive step in the notebook rather than in a side script, so the report's numbers come from the report's code.

### Challenge 5: Writing Analysis Before the Numbers Existed

**Symptom:** Q3 (best model), Q7 (feature comparison) and Q8 (feature reduction) demand concrete figures - per-model test F-scores, the model's actual top-5 features - but the notebook only *plots* the first and only prints the ranking if you add a print statement.

**Fix:** Two moves: (a) added an explicit top-5 ranking print in the feature-importance cell so the ranking is captured in the executed output itself; (b) recomputed the per-model 1%/10%/100% metrics from the raw CSV with identical preprocessing and seeds, so every claim in the prose ("0.7395 vs 0.6813 and 0.6826") is backed by reproducible digits rather than eyeballed chart heights.

**Takeaway:** Instrument outputs for the answers you will have to write, and never estimate a number you can compute.

### Challenge 6: The Model Disagreed With My Feature Ranking

**Symptom:** My blind Q6 ranking put `capital-gain` first (the classic #1 feature for this dataset). The trained Gradient Boosting model instead ranked `marital-status_ Married-civ-spouse` first with weight 0.394 - nearly double the runner-up - with `capital-gain` third (0.200) and my picks `hours-per-week` and `occupation` absent from the top 5.

**Investigation:** Two effects explain it: (1) genuine signal - married-civ-spouse correlates strongly with prime-earning age, dual incomes and full-time work in this 1994 census; (2) measurement bias - tree `feature_importances_` is mean-decrease-in-impurity, which favors multi-category columns (marital-status has 7 levels) and splits correlated financial signal across `capital-gain` *and* `capital-loss`. `occupation`'s importance is likewise fragmented across 14 one-hot columns.

**Fix:** Documented the discrepancy honestly in Q7 - what matched (3 of 5: capital-gain, age, education-num), what surprised me, and why the ranking should be read as "what this model used," not pure causality.

**Takeaway:** When the model contradicts your intuition, the interesting answer is the explanation - that discussion is what Q7 is actually grading.

## 10. Retrospective

### What I'd Do Differently

1. **Check the environment before reading a single cell.** The missing ML stack was discovered at step 1 by luck of ordering; a habit of "import check first" would have made it step 0, alongside verifying wheel availability for an unreleased Python version (3.14).
2. **Add the evidence prints on day one.** The top-5 importance ranking print was added *after* I realized Q7 needed numbers. Any output an answer will quote should be printed by the cell that generates it, decided before execution - not patched in afterward.
3. **Write the answers that need no data first, in one batch.** Q2, Q4 and Q6 were written pre-execution and Q3/Q5/Q7/Q8 post-execution; grouping them that way worked, but planning *which* answers are data-dependent up front would have made the two-pass structure deliberate rather than discovered.
4. **Trust but verify documentation.** The README's "~32,000 records" versus the actual 45,222 was a small thing, but it is a reminder that starter docs drift; the data file is the only source of truth worth computing from.

### What Worked Well

1. **Read everything before editing anything.** Reading the full notebook, the rubric, `visuals.py` and the raw CSV first surfaced the cell-order dependency (`income_raw` defined *below* the exploration cell), the label-format risk, and the real dataset size - all before any code was written.
2. **Sanity targets as de facto tests.** Hand-computing 45,222 / 11,208 / 24.78% and naive 0.2478 / 0.2917 in advance meant the first executed cell either confirmed the entire data path or exposed it immediately. It confirmed.
3. **One execution as the quality gate.** `nbconvert --execute` treats "it runs top to bottom" as binary, aborting on the first error. Landing the whole notebook - including the 135-fit grid search - in a single pass made the report's numbers internally consistent by construction.
4. **Numbers before prose.** Recomputing the learning curves with identical seeds, instead of describing a chart, turned every analysis paragraph into a verifiable claim - and the recomputation doubled as an independent check of the notebook itself.
5. **Constraint discipline.** `visuals.py` untouched, `max_features` untuned, `random_state=42` and `beta=0.5` everywhere, nothing committed: constraints are cheap to honor when you check them mechanically (`git diff`, stub scans) rather than from memory.

### The AI Partnership

> "AI is a fast, tireless analyst-engineer. It will fill every TODO, draft every answer, and write its own verification scripts faster than you can read them - but it needs you to set the acceptance criteria first (exact metrics, rubric wording, seed values, which files are frozen), and to verify the finished artifact afterward. The judgment layer - what to measure, what to trust, what to leave alone - stays human."

That pattern held throughout this project. The AI produced the cell implementations, the rubric-mapped prose, and the checks; human judgment supplied the decisions the brief left open (where `report.html` goes, global vs. venv installs), enforced numbers-before-prose, and insisted on `visuals.py` staying frozen despite its warnings. The best example was Challenge 6: the model flatly disagreed with my feature ranking, and the useful outcome was not "who was right" but a documented, evidence-backed explanation of *why* - which is exactly what the rubric's Q7 asks for.

### Final Thoughts

Finding Donors for CharityML is small enough to fit in one notebook, yet it exercises the full supervised-learning loop a real project demands: establish a naive floor, preprocess defensively, compare candidates on a shared pipeline, let learning curves expose overfitting, tune with cross-validation instead of hope, and interpret the winner - including when the interpretation contradicts your priors.

The review phase is what made it defensible: every claim traceable to a printed number, every rubric line backed by executed evidence, and two clean deliverables (the executed notebook and `docs/report.html`). The lesson generalizes beyond ML: in AI-assisted work, the human sets the contract and verifies the artifact - the AI multiplies the speed, not the judgment.
